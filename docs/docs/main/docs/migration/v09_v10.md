# From v0.9 to v0.10

Use this guide to update an existing RMK v0.9 firmware project. For new projects, follow the current [processor guide](../features/processor).

## Processors

Update registration first, then choose whether to keep your existing run loop.

### Remove registration mode arguments

In each `keyboard.toml` keyboard module, replace `#[register_processor(event)]` or `#[register_processor(poll)]` with the bare attribute:

```diff
- #[register_processor(event)]
+ #[register_processor]
```

Registration now starts the type's `Runnable` implementation. Check the type's `#[processor]` options to preserve the behavior you want:

| Previous setup                                   | What to keep or change                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `(poll)` with a polling processor                | Keep `poll_interval` and `poll()`.                                                                  |
| `(event)` with an event-only processor           | Keep `subscribe` without timer options.                                                             |
| `(event)` used to bypass the type's polling loop | Remove `poll_interval` to keep event-only behavior.                                                 |
| A type with a custom `Runnable`                  | Keep that implementation and its `#[runnable_generated]` marker; registration now starts your loop. |

Rust API projects that already use `run_all!` do not need a registration change.

### Use the generated deadline loop

Existing `DeadlineProcessor::deadline()` and `on_deadline()` methods keep their names. If you want RMK to generate the run loop for an existing deadline processor:

1. Add `deadline` to its `#[processor]` attribute.
2. Keep `deadline()` and `on_deadline()` in `impl DeadlineProcessor`.
3. Remove the old `impl Runnable` and `#[runnable_generated]` marker.

Keep the marker and `impl Runnable` if your custom loop is still needed. The [inactivity example](../features/processor#handle-inactivity) shows a complete processor with the generated loop.

## Sticky Key

`OSM(...)` and `OSL(...)` bindings remain supported. Update their configuration to use Sticky Key.

### Update `keyboard.toml`

Replace `[behavior.one_shot]` and `[behavior.one_shot_modifiers]` with `[behavior.sticky_key]`:

| v0.9 setting            | Change in `[behavior.sticky_key]`                                                                                                                                             |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `timeout`               | Rename to `wait_timeout`.                                                                                                                                                     |
| `activate_on_keypress`  | Remove. Sticky actions always activate on press.                                                                                                                              |
| `quick_release = true`  | Set `release_on = ["after_next_press"]`.                                                                                                                                      |
| `quick_release = false` | Remove to use the default `release_on = ["after_next_release"]`. The action stays active until the next input is released, including for other keys pressed during that hold. |

Two other behavior changes may require configuration:

- Modifier keys now count as input for release conditions. Add modifiers to `ignore`, such as `["LCtrl", "LShift"]`, to keep them from ending a sticky action.
- Holding a sticky key for at least `hold_timeout` (default `"250ms"`) ends the action when that key is released. Set `hold_timeout = "0ms"` to disable this duration check.

For custom profiles and all available settings, see [Sticky Key configuration](../configuration/behavior#profile-configuration).

### Update Rust bindings and configuration

Replace the removed one-shot actions with these macros:

| Removed action                       | Replacement                                |
| ------------------------------------ | ------------------------------------------ |
| `Action::OneShotModifier(modifiers)` | `rmk::osm!(modifiers)`                     |
| `Action::OneShotLayer(layer)`        | `rmk::osl!(layer)`                         |
| `Action::OneShotKey(key)`            | `rmk::sk!(Action::Key(KeyCode::Hid(key)))` |

The macros return `KeyAction`, so remove any surrounding `KeyAction::Single(...)`.
They use the default profile unless a profile index is supplied as the second argument.

Replace `BehaviorConfig::one_shot` and `BehaviorConfig::one_shot_modifiers` with
`BehaviorConfig::sticky_key`. Set the waiting timeout through `default_profile.wait_timeout_ms`,
in milliseconds. See [Configure a profile in Rust](../configuration/behavior#configure-a-profile-in-rust)
for profile setup.
