# From v0.9 to v0.10

Apply the changes below when upgrading firmware written for RMK v0.9. For examples of the current processor API, see [processors](../features/processor).

## Processors

### Register the type's Runnable

For `keyboard.toml` projects, remove the mode argument from each `#[register_processor]` attribute:

```diff
- #[register_processor(event)]
+ #[register_processor]
```

Make the same change for `#[register_processor(poll)]`. Registration now runs the type's `Runnable` implementation. Choose scheduling on the type's `#[processor]` attribute:

- For event handling only, use `subscribe` without timer options.
- For periodic work, keep or add `poll_interval` and provide `poll()`.
- For a resettable timeout, add `deadline` and provide `deadline()` and `on_deadline()`.

If `(event)` previously bypassed a type's polling behavior, remove `poll_interval` from the type to keep it event-only. If the type provides a custom `Runnable`, registration now runs that implementation.

### Rename manually implemented deadline methods

Update the methods in hand-written `DeadlineProcessor` implementations and any direct calls to those trait methods:

| v0.9 method                        | v0.10 method                           |
| ---------------------------------- | -------------------------------------- |
| `DeadlineProcessor::deadline()`    | `DeadlineProcessor::next_deadline()`   |
| `DeadlineProcessor::on_deadline()` | `DeadlineProcessor::handle_deadline()` |

Existing calls to `deadline_loop()` can stay as they are.

These renames apply to the trait methods. The inherent callbacks used by `#[processor(deadline)]` are still named `deadline()` and `on_deadline()`. To let the macro generate the traits and run loop, follow the [deadline processor example](../features/processor#deadline-processor).

## Battery setup

### Move GPIO setup out of BleBatteryConfig

For Rust API projects, `BleBatteryConfig` now controls BLE reporting only. It has no GPIO fields or lifetime parameter.

1. Replace `BleBatteryConfig::new(...)` with `BleBatteryConfig::default()` in your `RmkConfig`. Use `BleBatteryConfig::disabled()` if you want notifications disabled.
2. If the previous charging-state pin was `Some(pin)`, create `ChargingStateReader::new(pin, low_active)` using that pin and its polarity.
3. If the previous charging LED was `Some(pin)`, create `BatteryLedProcessor::new(pin, low_active)` using that pin and its polarity.
4. Run those components alongside one `BatteryProcessor` in your existing `run_all!` call. Omit a reader or LED when its old pin was `None`.
5. Remove the lifetime argument from explicit `BleBatteryConfig<'a>` type annotations.

For a complete task-list example, see [using the Rust API](../configuration/wireless#using-the-rust-api).

With ADC measurement, keep the ADC input task and use `BatteryProcessor::new(measured, total)` instead. For the internal VDDH input, use `BatteryProcessor::new(1, 5)`: the processor no longer guesses the divider from the sampled value.

### Keep existing TOML charger settings

The `[ble].charge_state` and `[ble].charge_led` keys keep their syntax. RMK constructs and runs the battery components for you. No Rust GPIO setup is needed in a TOML project.

Split boards can also configure those keys under `[split.central]` and `[[split.peripheral]]`. See [split battery configuration](../configuration/wireless#split-battery-configuration) for the override rules.
