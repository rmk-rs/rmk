# From v0.9 to v0.10

Use this guide to update an existing RMK v0.9 firmware project. For new projects, follow the current [processor guide](../features/processor).

## Processors

Update registration first, then choose whether to keep your existing run loop.

### Remove registration mode arguments

In each `keyboard.toml` keyboard module, replace `#[register_processor(event)]` or `#[register_processor(poll)]` with the bare attribute:

```diff
- #[register_processor(event)]
+ #[register_processor]
```

Registration now starts the type's `Runnable` implementation. Check the type's `#[processor]` options to preserve the behavior you want:

| Previous setup                                   | What to keep or change                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `(poll)` with a polling processor                | Keep `poll_interval` and `poll()`.                                                                  |
| `(event)` with an event-only processor           | Keep `subscribe` without timer options.                                                             |
| `(event)` used to bypass the type's polling loop | Remove `poll_interval` to keep event-only behavior.                                                 |
| A type with a custom `Runnable`                  | Keep that implementation and its `#[runnable_generated]` marker; registration now starts your loop. |

Rust API projects that already use `run_all!` do not need a registration change.

### Use the generated deadline loop

Existing `DeadlineProcessor::deadline()` and `on_deadline()` methods keep their names. If you want RMK to generate the run loop for an existing deadline processor:

1. Add `deadline` to its `#[processor]` attribute.
2. Keep `deadline()` and `on_deadline()` in `impl DeadlineProcessor`.
3. Remove the old `impl Runnable` and `#[runnable_generated]` marker.

Keep the marker and `impl Runnable` if your custom loop is still needed. The [inactivity example](../features/processor#handle-inactivity) shows a complete processor with the generated loop.

## Battery configuration tables

Battery settings now require a dedicated table for each board. Battery fields under `[ble]`, `[split.central]`, or `[[split.peripheral]]` are no longer accepted.

Move each board's battery settings to its battery table:

| Board            | Move fields from                                                    | Move fields to                                |
| ---------------- | ------------------------------------------------------------------- | --------------------------------------------- |
| Unibody          | `[ble]`                                                             | `[battery]`                                   |
| Split central    | `[split.central]`, plus any battery settings inherited from `[ble]` | `[split.central.battery]`                     |
| Split peripheral | Its `[[split.peripheral]]` entry                                    | `[split.peripheral.battery]` below that entry |

Move `battery_adc_pin`, `adc_divider_measured`, `adc_divider_total`, `charge_state`, `charge_led`, and `battery_user_description` if configured. Leave BLE connection and pairing settings in `[ble]`.

For example, a unibody configuration changes as follows:

```diff
 [ble]
 enabled = true
+
+[battery]
 battery_adc_pin = "P0_05"
 adc_divider_measured = 2000
 adc_divider_total = 2806
```

Remove the battery fields from their old sections after moving them. Peripherals use only their own battery table and never inherit the central's battery configuration.

See [Battery configuration](../configuration/wireless#battery-configuration) for field descriptions and split keyboard examples.

## Serial numbers

Serial numbers no longer contain the RMK version. USB, BLE, and Rynk report the same protocol marker and device ID. See [About serial numbers](../configuration/keyboard_device#about-serial-numbers).

Default serial numbers change as follows:

- nRF BLE builds keep their hardware ID. Vial serials stay the same; Rynk BLE serials gain the `rynk:` prefix.
- Other defaults change from the version stamp to a hardware ID or the `RMK` fallback.

Existing Vial and Rynk markers in configured IDs are replaced automatically.

To update your project:

1. If an nRF BLE keyboard sets `serial_number`, remove the override to keep using its hardware ID. Older firmware ignored the override.
2. Remove `RMK_BUILD_INFO`. Omit `serial_number` to use the platform default.
3. For a custom ID in Rust, replace the string literal with `rmk::config::build_serial_number("board-0001")`, using your existing ID. The field now owns the complete serial number.
4. `DeviceConfig` is now `Clone` rather than `Copy`. When USB and BLE share a configuration, pass `rmk_config.device_config.clone()` to USB before moving `rmk_config` into BLE.

## `keyboard.toml` Update

### Migrate one-shot keys to Sticky Key

Keep `OSM(...)` and `OSL(...)` bindings. Replace `[behavior.one_shot]` and
`[behavior.one_shot_modifiers]` with `[behavior.sticky_key]`.

| Previous setting                                          | Migration                                                                               |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `timeout`                                                 | Rename to `wait_timeout`.                                                               |
| `activate_on_press` / `activate_on_keypress`              | Remove; sticky actions now start on press.                                              |
| `release_on_next_press = true` / `quick_release = true`   | Set `release_on = ["after_next_press"]`.                                                |
| `release_on_next_press = false` / `quick_release = false` | Choose `after_next_press` or `after_next_release`; deferred-report behavior is removed. |
| `release_on_layer = "enter"` / `"exit"` / `"both"`        | Add `layer_enter`, `layer_exit`, or both to `release_on`.                               |
| `release_on_layer = "none"`                               | Omit layer conditions.                                                                  |

After a short tap, the default sticky expires if no input consumes it within one second. Consumption
stops the timer; the action lasts until that input releases, affecting overlapping keys too.

Modifiers now consume stickies. Add modifiers to `ignore` to keep stacking them, for example
`ignore = ["LShift", "LCtrl"]`. Hold detection uses `hold_timeout` (default `"250ms"`),
independently of Morse.

See [Sticky Key](../configuration/behavior#sticky-key) for examples and all settings. Arrays replace
inherited values: retain the desired key condition when adding a layer condition, such as
`release_on = ["after_next_release", "layer_exit"]`.

For Rust configurations, replace `Action::OneShotLayer`, `Action::OneShotModifier` and
`Action::OneShotKey` with `KeyAction::Sticky(Action, profile_index)`. `StickyProfile` now uses
`release_on` (`StickyReleaseConditions`), `ignore` (`KeyCode` values), `wait_timeout_ms` and
`hold_timeout_ms`. See
[Configure a profile in Rust](../configuration/behavior#configure-a-profile-in-rust).
