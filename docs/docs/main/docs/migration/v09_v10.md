# From v0.9 to v0.10

Use this guide to update an existing RMK v0.9 firmware project. For new projects, follow the current [processor guide](../features/processor).

## Processors

Update registration first, then choose whether to keep your existing run loop.

### Remove registration mode arguments

In each `keyboard.toml` keyboard module, replace `#[register_processor(event)]` or `#[register_processor(poll)]` with the bare attribute:

```diff
- #[register_processor(event)]
+ #[register_processor]
```

Registration now starts the type's `Runnable` implementation. Check the type's `#[processor]` options to preserve the behavior you want:

| Previous setup                                   | What to keep or change                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `(poll)` with a polling processor                | Keep `poll_interval` and `poll()`.                                                                  |
| `(event)` with an event-only processor           | Keep `subscribe` without timer options.                                                             |
| `(event)` used to bypass the type's polling loop | Remove `poll_interval` to keep event-only behavior.                                                 |
| A type with a custom `Runnable`                  | Keep that implementation and its `#[runnable_generated]` marker; registration now starts your loop. |

Rust API projects that already use `run_all!` do not need a registration change.

### Use the generated deadline loop

Existing `DeadlineProcessor::deadline()` and `on_deadline()` methods keep their names. If you want RMK to generate the run loop for an existing deadline processor:

1. Add `deadline` to its `#[processor]` attribute.
2. Keep `deadline()` and `on_deadline()` in `impl DeadlineProcessor`.
3. Remove the old `impl Runnable` and `#[runnable_generated]` marker.

Keep the marker and `impl Runnable` if your custom loop is still needed. The [inactivity example](../features/processor#handle-inactivity) shows a complete processor with the generated loop.
